# Contributing to apim-claude-template

---

## Checklist: creating a new `api-cp-*` or `service-cp-*` repo

Complete these steps **before other team members start working on the repo**.
The template file must exist in `apim-claude-template` before anyone can run `/setup-claude-md`.

### Step 1 — Clone the new repo as a sibling

All repos must sit in the same parent directory as `apim-claude-template`:

```
~/HMCTS/APIM/
├── apim-claude-template/
├── api-cp-<new-name>/        ← new repo here
└── ...
```

```bash
cd ~/HMCTS/APIM
git clone git@github.com:hmcts/api-cp-<new-name>.git
```

### Step 2 — Generate the repo-specific template

Open the new repo in Claude Code and run:

```bash
cd api-cp-<new-name>
/generate-repo-doc
```

The skill reads the real source files (OpenAPI spec, `build.gradle`, test classes, CI workflows)
and writes `apim-claude-template/templates/repos/api-cp-<new-name>.md`, then commits it
to `apim-claude-template` automatically.

> If the repo has no OpenAPI spec yet (skeleton only), run `/generate-repo-doc` again
> once the spec is added — it overwrites safely.

### Step 3 — Raise a PR on apim-claude-template

```bash
cd ../../apim-claude-template
git checkout -b dev/add-api-cp-<new-name>
git push -u origin dev/add-api-cp-<new-name>
gh pr create \
  --base master \
  --title "feat: add repo template for api-cp-<new-name>" \
  --body "Auto-generated by /generate-repo-doc. Review for accuracy before merging."
```

Get the PR reviewed and merged before telling the team the repo is ready to work on.

### Step 4 — Set up your local Claude context

```bash
cd ../api-cp-<new-name>
/setup-claude-md
```

This writes `.claude/CLAUDE.md` (gitignored) with three `@import` lines pointing at the
shared templates. Claude Code picks them up on every session — no further action needed.

### Step 5 — Tell the team

Share the repo link. Each developer runs `/setup-claude-md` once in the repo on their
own machine — that's all they need to do.

## Checklist: existing repo, architecture has changed

Run this whenever endpoints, environment variables, infrastructure, or test structure
change significantly in a repo.

```bash
cd api-cp-<repo-name>
/generate-repo-doc
```

Then raise a PR on `apim-claude-template` for the regenerated file (same as Step 3 above).

---

## Checklist: updating shared templates

For changes that apply to all repos (code rules, API patterns, service patterns):

```bash
cd apim-claude-template
git checkout -b dev/<description>

# Edit the relevant file:
# - All repos:         templates/shared-code-rules.md
# - All api-cp-*:     templates/api-spec-shared.md
# - All service-cp-*: templates/service-shared.md
# - Review policies:  skills/openapi-spec-reviewer/knowledge/

git add templates/   # or skills/
git commit -m "feat: ..."
git push -u origin dev/<description>
gh pr create --base master --title "..."
```

One merged PR delivers the change to all repos on their next Claude Code session.

## Checklist: adding or modifying a skill

```bash
cd apim-claude-template
git checkout -b dev/<skill-name>-<change>

# Edit or create:
# - skills/<skill-name>/SKILL.md          ← skill logic
# - skills/<skill-name>/knowledge/*.md    ← policy knowledge files (if applicable)
# - .claude-plugin/marketplace.json       ← register new skills here

git add skills/ .claude-plugin/
git commit -m "feat: ..."
git push -u origin dev/<skill-name>-<change>
gh pr create --base master --title "..."
```

---

## Branch naming

| Change type | Branch pattern |
|---|---|
| New repo template | `dev/add-<repo-name>` |
| Regen existing template | `dev/regen-<repo-name>` |
| Shared template update | `dev/update-<template-name>` |
| New or changed skill | `dev/<skill-name>-<change>` |
| Bug fix | `fix/<description>` |

---

## PR requirements

- Target branch: `master`
- At least 1 approval required (branch protection enforced)
- Title must follow `feat:` / `fix:` / `docs:` / `chore:` convention
- For generated repo template files: note in the PR body whether the repo
  had a full OpenAPI spec at generation time, or whether it will need
  regenerating once the spec is complete
